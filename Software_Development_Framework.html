📏 PEP 8 Style Guide

PEP 8 is the official style guide for Python code. Written by Guido van Rossum (Python's creator), Barry Warsaw, and Nick Coghlan, it covers how to format Python code for maximum readability and consistency. Following PEP 8 is not just about aesthetics — it makes code easier to review, maintain, and collaborate on.

ℹ️ Why PEP 8 Matters

Code is read many more times than it is written. PEP 8 exists to help developers write code that is readable by other Python programmers. When all code in a project follows the same conventions, it becomes easier to understand at a glance, reducing cognitive load and review time.

Core PEP 8 Principles

❌ BAD — PEP 8 Violations
# Wrong indentation (2 spaces) def calculate_area(width,height): return width*height # Multiple imports on one line import os, sys, json # Spaces around = in keyword args print(end = '\n', sep = ',') # No spaces around operators x=1+2 y=x*3 # Trailing whitespace and extra blank lines class MyClass: def method_one(self): pass def method_two(self): pass # Line too long (>79 chars) result = some_function(argument_one, argument_two, argument_three, argument_four, keyword=value)
✅ GOOD — PEP 8 Compliant
# Correct indentation (4 spaces) def calculate_area(width: float, height: float) -> float: return width * height # One import per line import json import os import sys # No spaces in keyword args print(end='\n', sep=',') # Spaces around operators x = 1 + 2 y = x * 3 # Two blank lines between top-level defs class MyClass: def method_one(self): pass def method_two(self): pass # Break long lines with backslash or parens result = some_function( argument_one, argument_two, argument_three, argument_four, keyword=value, )
💜 Pro Tip: Automate PEP 8

Don't manually check PEP 8 compliance — use Black (auto-formatter), Ruff (fast linter), and configure them in your pyproject.toml. Run them in pre-commit hooks so PEP 8 is enforced automatically before every commit.

🏷️ Naming Conventions

Consistent naming is one of the most impactful readability improvements you can make. Python has clear conventions defined in PEP 8 for different identifier types.

Identifier Type Convention ✅ Good Examples ❌ Bad Examples
Variables snake_case user_name, total_count, is_active userName, TotalCount, isactive
Functions snake_case get_user(), calculate_total(), send_email() GetUser(), calculateTotal(), SendEmail()
Classes PascalCase UserService, DatabaseConnection, HttpClient user_service, database_connection, http_client
Constants UPPER_SNAKE_CASE MAX_RETRY_COUNT, DEFAULT_TIMEOUT, BASE_URL maxRetryCount, default_timeout, baseUrl
Modules snake_case user_service.py, data_processor.py UserService.py, DataProcessor.py
Packages lowercase utils, models, services Utils, Models, ServiceLayer
Private attrs _single_leading _internal_state, _cache internal_state, cache__
Name mangled __double_leading __secret, __private_method ___triple, PRIVATE
Magic methods __dunder__ __init__, __str__, __repr__ init, to_string, repr
Type vars PascalCase single letters T, KT, VT, UserT type_var, t, TYPE

Naming Examples in Context

# ✅ Complete example showing all naming conventions together from typing import Optional, TypeVar, Generic, Protocol # Module-level constants MAX_CONNECTIONS: int = 100 DEFAULT_TIMEOUT_SECONDS: float = 30.0 BASE_API_URL: str = "https://api.example.com/v1" # TypeVar for generic code T = TypeVar("T") UserT = TypeVar("UserT", bound="BaseUser") class DatabaseConnection: """Manages database connections with connection pooling.""" # Class-level constants MAX_POOL_SIZE: int = 10 MIN_POOL_SIZE: int = 2 def __init__(self, connection_string: str, pool_size: int = 5) -> None: self.connection_string = connection_string self.pool_size = pool_size self._active_connections: list[object] = [] # private self.__master_key: str = "" # name-mangled def get_connection(self) -> Optional[object]: # snake_case for function names return self._fetch_from_pool() def release_connection(self, conn: object) -> None: self._return_to_pool(conn) def _fetch_from_pool(self) -> Optional[object]: # Single underscore = internal method if self._active_connections: return self._active_connections.pop() return None def _return_to_pool(self, conn: object) -> None: self._active_connections.append(conn) def __repr__(self) -> str: # Dunder method for string representation return f"DatabaseConnection(pool_size={self.pool_size})" def calculate_connection_health_score( total_connections: int, failed_connections: int, response_time_ms: float, ) -> float: # Local variables use snake_case failure_rate = failed_connections / max(total_connections, 1) latency_penalty = min(response_time_ms / 1000, 1.0) health_score = (1 - failure_rate) * (1 - latency_penalty) return round(health_score * 100, 2)
⚠️ Common Naming Pitfalls
  • Never use l (lowercase L), O (uppercase O), or I (uppercase I) as single-character variable names — they're visually ambiguous with 1 and 0
  • Avoid abbreviations unless they're widely understood (e.g., http, url, api are OK; usr, cnt are not)
  • Don't shadow built-in names: list, dict, type, id, input, filter
  • Don't prefix with my_ or the_ — be specific: active_users not my_users

📝 String Formatting

Python offers three main approaches to string formatting. Each has its place, but f-strings (introduced in Python 3.6) are the preferred modern approach for their readability and performance.

F-strings (Preferred — Python 3.6+)

✅ F-strings: Most Readable and Performant
# Basic f-string name = "Alice" age = 30 greeting = f"Hello, {name}! You are {age} years old." # Expressions inside f-strings items = [1, 2, 3, 4, 5] result = f"Sum: {sum(items)}, Count: {len(items)}" # Format specifiers price = 9.99 pi = 3.14159265 print(f"Price: ${price:.2f}") # Price: $9.99 print(f"Pi: {pi:.4f}") # Pi: 3.1416 print(f"Big number: {1000000:,}") # Big number: 1,000,000 print(f"Percent: {0.7523:.1%}") # Percent: 75.2% print(f"Hex: {255:#x}") # Hex: 0xff print(f"Padded: {name:<20}|") # Padded: Alice | print(f"Centered: {name:^20}|") # Centered: Alice | # Multi-line f-strings report = ( f"User Report\n" f"-----------\n" f"Name: {name}\n" f"Age: {age}\n" f"Items count: {len(items)}" ) # Python 3.12+ f-string debugging with = x = 42 y = 58 print(f"{x=}, {y=}, {x+y=}") # x=42, y=58, x+y=100 # Nested quotes in f-strings (Python 3.12+) items_str = f"Items: {[i**2 for i in range(5)]}"

.format() Method (Legacy — Avoid in New Code)

# .format() — still works but verbose compared to f-strings name = "Bob" age = 25 # Positional arguments msg = "Hello, {}! You are {} years old.".format(name, age) # Named arguments (better for readability) msg = "Hello, {name}! You are {age} years old.".format(name=name, age=age) # With format spec msg = "Price: ${price:.2f}".format(price=9.99) # When .format() is useful: template strings defined externally TEMPLATE = "Dear {recipient}, your order {order_id} is ready." email_body = TEMPLATE.format(recipient="Alice", order_id="ORD-123")

% Formatting (Old Style — Do Not Use)

❌ BAD — % Formatting (C-style, Avoid in Python)
# % formatting — legacy, C-style, NOT Pythonic name = "Carol" age = 35 msg = "Hello, %s! You are %d years old." % (name, age) price = "Price: $%.2f" % 9.99 # ONLY acceptable use: logging module (lazy evaluation) import logging logger = logging.getLogger(__name__) logger.debug("Processing user %s with id %d", username, user_id) # ↑ This is correct for logging — avoids formatting cost if DEBUG is off
💜 Pro Tip: String Concatenation Performance
# ❌ Slow: String concatenation in a loop creates many temporary objects result = "" for i in range(1000): result += f"item{i}" # ✅ Fast: Use join() with a list comprehension result = "".join(f"item{i}" for i in range(1000)) # ✅ Fast: Use io.StringIO for very large strings import io buffer = io.StringIO() for i in range(10000): buffer.write(f"item{i}") result = buffer.getvalue()
🔷 Type Hints

Type hints (PEP 484) enable static type checking with tools like mypy and pyright, improving code documentation, IDE autocompletion, and catching bugs before runtime. They are not enforced at runtime but provide enormous value during development.

📖 Docstrings

Docstrings are the primary means of documenting Python code. They're accessible at runtime via help(), used by IDEs for hover documentation, and can be processed by documentation generators like Sphinx. There are three main docstring styles.

Google Style (Recommended)

def calculate_compound_interest( principal: float, rate: float, periods: int, compounds_per_year: int = 12, ) -> float: """Calculate compound interest for a given principal and rate. Uses the standard compound interest formula: A = P * (1 + r/n)^(n*t) Args: principal: The initial investment amount in dollars. Must be positive. rate: Annual interest rate as a decimal (e.g., 0.05 for 5%). Must be between 0 and 1 inclusive. periods: Number of years the money is invested. Must be positive. compounds_per_year: Number of times interest is compounded per year. Defaults to 12 (monthly). Common values: 1 (annually), 4 (quarterly), 12 (monthly), 365 (daily). Returns: The total amount (principal + interest) after the specified number of periods, rounded to 2 decimal places. Raises: ValueError: If principal is not positive, rate is outside [0, 1], or periods is not positive. TypeError: If any argument is not of the expected numeric type. Examples: >>> calculate_compound_interest(1000, 0.05, 10) 1647.01 >>> calculate_compound_interest(5000, 0.03, 5, compounds_per_year=4) 5805.92 >>> calculate_compound_interest(0, 0.05, 10) Traceback (most recent call last): ... ValueError: Principal must be positive, got 0 Note: This function does not account for inflation or taxes. For financial planning, consult a certified financial advisor. """ if principal <= 0: raise ValueError(f"Principal must be positive, got {principal}") if not 0 <= rate <= 1: raise ValueError(f"Rate must be between 0 and 1, got {rate}") if periods <= 0: raise ValueError(f"Periods must be positive, got {periods}") amount = principal * (1 + rate / compounds_per_year) ** (compounds_per_year * periods) return round(amount, 2)

NumPy Style (Common in Scientific Python)

import numpy as np def normalize_array( arr: np.ndarray, axis: int = 0, eps: float = 1e-8, ) -> np.ndarray: """Normalize an array to have zero mean and unit variance. Parameters ---------- arr : np.ndarray The input array to normalize. Can be 1D, 2D, or higher dimensional. Non-numeric dtypes will raise a TypeError. axis : int, optional The axis along which to compute mean and standard deviation. Defaults to 0 (normalize along rows for 2D arrays). eps : float, optional Small epsilon value added to denominator to avoid division by zero. Defaults to 1e-8. Returns ------- np.ndarray Normalized array with same shape as input. Each element is transformed to (x - mean) / (std + eps). Raises ------ TypeError If arr contains non-numeric values. See Also -------- np.mean : Compute mean along an axis. np.std : Compute standard deviation along an axis. sklearn.preprocessing.StandardScaler : For scikit-learn compatible scaling. ⚠️ Exception Handling

try/except/else/finally Pattern

import logging from pathlib import Path logger = logging.getLogger(__name__) def read_config_file(config_path: str) -> dict: """Read and parse a JSON configuration file.""" file_path = Path(config_path) try: # try: code that might raise exceptions content = file_path.read_text(encoding="utf-8") config = json.loads(content) except FileNotFoundError: # Specific exception — file doesn't exist logger.error("Config file not found: %s", config_path) raise # Re-raise to let caller handle it except PermissionError as e: # Specific exception with access to the error logger.error("Permission denied reading config: %s", e) raise RuntimeError(f"Cannot read config file: {config_path}") from e except json.JSONDecodeError as e: # Multiple specific exceptions logger.error("Invalid JSON in config file %s: %s", config_path, e) raise ValueError(f"Config file contains invalid JSON: {e.msg} at line {e.lineno}") from e except (IOError, OSError) as e: # Catch multiple exceptions in a tuple logger.error("IO error reading config: %s", e) raise else: # else: runs ONLY if no exception was raised logger.info("Successfully loaded config from %s", config_path) return config finally: # finally: ALWAYS runs — use for cleanup logger.debug("Config read attempt completed for: %s", config_path)

Custom Exception Hierarchy

# Define a base exception for your application domain class AppError(Exception): """Base exception for all application errors.""" def __init__(self, message: str, error_code: str = "UNKNOWN") -> None: super().__init__(message) self.message = message self.error_code = error_code def __str__(self) -> str: return f"[{self.error_code}] {self.message}" # Domain-specific exceptions class ValidationError(AppError): """Raised when input validation fails.""" def __init__(self, field: str, value: Any, reason: str) -> None: super().__init__( message=f"Validation failed for '{field}': {reason} (got: {value!r})", error_code="VALIDATION_ERROR", ) self.field = field self.value = value self.reason = reason class NotFoundError(AppError): """Raised when a requested resource is not found.""" def __init__(self, resource_type: str, resource_id: str | int) -> None: super().__init__( message=f"{resource_type} with id '{resource_id}' was not found", error_code="NOT_FOUND", ) self.resource_type = resource_type self.resource_id = resource_id class AuthenticationError(AppError): """Raised when authentication fails.""" def __init__(self, reason: str = "Invalid credentials") -> None: super().__init__(message=reason, error_code="AUTH_FAILED") class AuthorizationError(AppError): """Raised when a user lacks permission for an action.""" def __init__(self, action: str, resource: str) -> None: super().__init__( message=f"Not authorized to {action} on {resource}", error_code="FORBIDDEN", ) # Usage example def get_user(user_id: int) -> dict: if user_id <= 0: raise ValidationError("user_id", user_id, "must be positive") user = db.find(user_id) if not user: raise NotFoundError("User", user_id) return user
⚠️ Exception Handling Anti-Patterns
# ❌ NEVER catch bare Exception or BaseException silently try: risky_operation() except: # Catches EVERYTHING including KeyboardInterrupt! pass # Silent failure is the worst kind # ❌ Don't catch Exception too broadly try: result = process_data(data) except Exception: return None # You'll never know WHY it failed # ✅ Catch specific exceptions, log appropriately try: result = process_data(data) except ValueError as e: logger.error("Invalid data format: %s", e, exc_info=True) raise

🏗️ SOLID Principles
ℹ️ What is SOLID?

SOLID is an acronym for five object-oriented design principles that make software designs more understandable, flexible, and maintainable. They were introduced by Robert C. Martin (Uncle Bob) and are fundamental to professional software engineering.

S — Single Responsibility Principle

A class should have only one reason to change — it should do one thing and do it well.

❌ BEFORE — Violates SRP
class UserManager: # Does TOO MANY things! def create_user(self, data): ... def send_welcome_email(self, user): ... def save_to_database(self, user): ... def generate_pdf_report(self): ... def log_activity(self, action): ...
✅ AFTER — Each class has one job
class UserService: def create_user(self, data): ... class EmailService: def send_welcome(self, user): ... class UserRepository: def save(self, user): ... class ReportGenerator: def generate_pdf(self): ... class ActivityLogger: def log(self, action): ...

O — Open/Closed Principle

Software entities should be open for extension but closed for modification.

from abc import ABC, abstractmethod # ❌ BEFORE — Adding new discount type requires modifying existing code def calculate_discount_bad(order, discount_type: str) -> float: if discount_type == "student": return order.total * 0.1 elif discount_type == "senior": return order.total * 0.15 elif discount_type == "employee": # Added later — modifies existing! return order.total * 0.25 return 0 # ✅ AFTER — Open for extension via new subclasses, closed for modification class DiscountStrategy(ABC): @abstractmethod def calculate(self, order_total: float) -> float: ... class StudentDiscount(DiscountStrategy): def calculate(self, order_total: float) -> float: return order_total * 0.10 class SeniorDiscount(DiscountStrategy): def calculate(self, order_total: float) -> float: return order_total * 0.15 # Adding new discount — NO modification to existing code needed! class EmployeeDiscount(DiscountStrategy): def calculate(self, order_total: float) -> float: return order_total * 0.25 class PriceCalculator: def __init__(self, discount: DiscountStrategy) -> None: self.discount = discount def final_price(self, order_total: float) -> float: return order_total - self.discount.calculate(order_total)

L — Liskov Substitution Principle

Objects of a subclass must be substitutable for objects of the parent class without breaking behavior.

from dataclasses import dataclass # ❌ VIOLATION: Square breaks Rectangle behavior class Rectangle: def __init__(self, width: float, height: float): self.width = width self.height = height def area(self) -> float: return self.width * self.height class Square(Rectangle): # LSP VIOLATION! def __init__(self, size: float): super().__init__(size, size) @property # Setting width also changes height — unexpected! def width(self): return self._width @width.setter def width(self, val): self._width = self._height = val # BREAKS RECTANGLE CONTRACT # ✅ CORRECT: Use separate classes under a common abstraction class Shape(ABC): @abstractmethod def area(self) -> float: ... @abstractmethod def perimeter(self) -> float: ... @dataclass class GoodRectangle(Shape): width: float height: float def area(self) -> float: return self.width * self.height def perimeter(self) -> float: return 2 * (self.width + self.height) @dataclass class GoodSquare(Shape): side: float def area(self) -> float: return self.side ** 2 def perimeter(self) -> float: return 4 * self.side

I — Interface Segregation Principle

No code should be forced to depend on methods it does not use. Split large interfaces into smaller, specific ones.

from typing import Protocol # ❌ FAT INTERFACE — classes forced to implement irrelevant methods class AllInOneWorker(Protocol): def work(self) -> None: ... def eat(self) -> None: ... def sleep(self) -> None: ... def manage_team(self) -> None: ... def code_review(self) -> None: ... # ✅ SEGREGATED INTERFACES — each protocol does one job class Workable(Protocol): def work(self) -> None: ... class Eatable(Protocol): def eat(self) -> None: ... class Manageable(Protocol): def manage_team(self) -> None: ... def code_review(self) -> None: ... # Robot works but doesn't eat — no forced implementation class Robot: def work(self) -> None: print("Robot working") # Human eats and works class Developer: def work(self) -> None: print("Coding...") def eat(self) -> None: print("Eating lunch")

D — Dependency Inversion Principle

High-level modules should not depend on low-level modules. Both should depend on abstractions.

from abc import ABC, abstractmethod # ❌ BEFORE: High-level UserService tightly coupled to MySQL class MySQLDatabase: def save(self, data: dict) -> None: # MySQL-specific implementation ... class UserServiceBad: def __init__(self): self.db = MySQLDatabase() # HARDCODED — can't swap to Postgres! def create_user(self, data: dict) -> None: self.db.save(data) # ✅ AFTER: Depend on abstraction, inject implementation class Repository(ABC): """Abstract repository — the abstraction both depend on.""" @abstractmethod def save(self, data: dict) -> None: ... @abstractmethod def find_by_id(self, id: int) -> dict | None: ... class PostgresRepository(Repository): def save(self, data: dict) -> None: ... # Postgres implementation def find_by_id(self, id: int) -> dict | None: ... class InMemoryRepository(Repository): """Used in tests — no real database needed.""" def __init__(self) -> None: self._store: dict[int, dict] = {} def save(self, data: dict) -> None: self._store[data["id"]] = data def find_by_id(self, id: int) -> dict | None: return self._store.get(id) class UserServiceGood: def __init__(self, repository: Repository) -> None: self.repository = repository # Injected — can be any Repository! def create_user(self, data: dict) -> None: self.repository.save(data) # Production: use real database prod_service = UserServiceGood(repository=PostgresRepository()) # Testing: use in-memory fake test_service = UserServiceGood(repository=InMemoryRepository())

TDD: Red-Green-Refactor

ℹ️ TDD Workflow
🔴 RED — Write a failing test first

Write a test that describes the desired behavior. Run it — it should fail (the code doesn't exist yet). This confirms your test is testing the right thing.

🟢 GREEN — Write minimal code to pass

Write the simplest possible code that makes the test pass. Don't over-engineer. Just make it green.

🔵 REFACTOR — Clean up

Now that tests pass, refactor the code for quality. Add type hints, improve names, extract methods, remove duplication. Run tests again to ensure nothing broke.

💭 AI-Native Development Philosophy

We are living through a fundamental shift in how software is created. For decades, programming meant translating human intent into machine instructions, character by character, line by line. The developer served as the bridge between the human world of ideas and the machine world of syntax. But AI is rapidly collapsing this gap, enabling developers to express intent at a higher level of abstraction than ever before.

AI-native development is not merely about using AI as a fancy autocomplete. It represents a philosophical shift in how we think about the developer's role. Rather than being the primary producer of code, the AI-native developer becomes a director of code — someone who orchestrates AI capabilities, reviews generated solutions, ensures quality, and maintains domain expertise. The best analogy is an experienced architect who no longer draws every wall themselves but instead directs a team, reviews work, and ensures the building meets its purpose.

This shift carries both opportunity and responsibility. The opportunity is tremendous: developers who embrace AI tools effectively can achieve 2-10x productivity gains for certain types of tasks — particularly boilerplate code, test generation, documentation, and refactoring. Teams can deliver features faster, explore more solution paths, and spend more cognitive energy on genuinely hard problems: system design, user experience, performance optimization, and business logic. The responsibility is equally significant: with AI generating large amounts of code quickly, human review, critical thinking, and domain expertise become more important, not less.

The developers who will thrive in the AI-native era are those who maintain deep technical knowledge while mastering the art of AI collaboration — knowing when to trust AI suggestions, when to question them, how to prompt effectively, and how to build systems that are maintainable even when partially AI-generated. This guide is designed to help you develop exactly those skills.

🧠
Deep Knowledge Still Matters

AI tools work best for developers who deeply understand the code they're directing. AI amplifies expertise — it doesn't replace it.

🔍
Critical Review is Essential

AI-generated code must be reviewed as carefully as human-written code. AI can produce confident-sounding but subtly wrong solutions.

🎯
Intent Clarity is the New Skill

The ability to express clear, precise intent in natural language — prompting — is rapidly becoming a core developer competency.

🧠 What is Agentic AI?

Agentic AI refers to AI systems that can autonomously plan, take actions, use tools, observe results, and iterate toward a goal — without requiring human input at every step. Unlike simple autocompletion (which suggests the next few tokens), an agentic AI can be given a high-level task like "add a caching layer to this API endpoint" and will figure out the steps needed to accomplish it.

The AI Assistance Spectrum

Key Characteristics of Agentic AI Systems

🛠️
Tool Use

Agentic AI can use tools: read files, write files, execute terminal commands, search the web, call APIs, run tests, and interact with your development environment.

🔄
Iterative Execution

Agents don't give up on the first attempt. They observe results, understand what went wrong, and try alternative approaches — just like a human developer debugging.

📋
Planning & Decomposition

Given a complex goal, an agent can break it down into subtasks, determine the order of operations, and execute them sequentially or in parallel.

🧩
Context Awareness

Modern agents understand the full context of a codebase — not just the file open in the editor, but project structure, dependencies, conventions, and related files.

🎵 Vibe Coding
ℹ️ Origin of the Term

"Vibe coding" was coined by Andrej Karpathy (former Tesla AI director, OpenAI co-founder) in early 2025. He described a mode of programming where you "fully give in to the vibes," accepting all AI suggestions, barely reading the code, describing changes in natural language, and running tests to see if things work. He noted this was fun for quick projects but questioned its suitability for production code.

The Vibe Coding Spectrum

🎵 Pure Vibe Coding (Risky)
  • Accept all AI suggestions without reading
  • Never understand why the code works
  • No testing strategy
  • Can't debug when things break
  • Security vulnerabilities go unnoticed
  • Technical debt accumulates invisibly
⚡ Responsible Vibe Coding (Recommended)
  • Use AI to accelerate — but read all suggestions
  • Understand the generated code before accepting
  • Review with a security mindset
  • Write tests to validate AI output
  • Maintain understanding of the full system
  • Track what AI generated for future reference

Risks of Unrestrained Vibe Coding

⚠️ The Comprehension Gap

The biggest risk of vibe coding is the comprehension gap — code exists in your codebase that no human fully understands. When this code breaks in production at 3am, nobody can fix it quickly because nobody understands it. AI-generated code without human comprehension is a liability, not an asset.

🔒
Security Risks

AI models can generate code with subtle security vulnerabilities: improper input validation, SQL injection vectors, insecure random number generation, hardcoded secrets in test code that gets committed.

💸
Technical Debt

AI-generated code is often "good enough" but not optimal. Without review, you accumulate N+1 queries, missing indexes, memory leaks, and inefficient algorithms that won't show up until scale.

🧠
Skill Atrophy

Developers who rely entirely on AI for core programming concepts may find their skills degrading. When AI fails or the context is too complex, they have no fallback.

Best Practices for Responsible AI-Assisted Coding

1
Read Every Line

Accept AI suggestions only after reading and understanding them. If you don't understand a suggestion, ask the AI to explain it before accepting.

2
Verify with Tests

Write unit tests for all AI-generated functions. Tests serve as executable documentation and catch subtle errors.

3
Security Review Every Suggestion

Ask yourself: Does this handle untrusted input safely? Does this expose sensitive data? Does this bypass authentication?

4
Don't Trust AI on Edge Cases

AI excels at happy paths but often misses edge cases: null values, empty collections, integer overflow, timezone issues, concurrent access.

5
Maintain Architectural Ownership

Let AI generate implementations, but you make architectural decisions. System design is where human judgment is most irreplaceable.

✅ 2xx Success
  • 200 OK — Standard success (GET, PUT, PATCH)
  • 201 Created — Resource created (POST)
  • 202 Accepted — Async task accepted
  • 204 No Content — Success, nothing to return (DELETE)
  • 206 Partial Content — Paginated response
⚠️ 4xx Client Errors
  • 400 Bad Request — Invalid request format
  • 401 Unauthorized — Not authenticated
  • 403 Forbidden — Not authorized
  • 404 Not Found — Resource doesn't exist
  • 409 Conflict — Duplicate resource
  • 422 Unprocessable — Validation failed
  • 429 Too Many Requests — Rate limited
🔴 5xx Server Errors
  • 500 Internal Server Error — Unexpected failure
  • 502 Bad Gateway — Upstream failure
  • 503 Service Unavailable — Maintenance or overload
  • 504 Gateway Timeout — Upstream timeout

📊 Monitoring and Observability
ℹ️ The Three Pillars of Observability

Modern systems require three complementary signals to fully understand their behavior: Metrics (what is happening — numbers over time), Logs (what happened — discrete events), and Traces (where it happened — request flow across services). Together, these enable teams to understand and debug complex distributed systems.

📊
Metrics

Tool: Prometheus + Grafana
Numeric time-series data: request count, latency (p50/p95/p99), error rate, CPU, memory, queue depth.
Key metrics to track: request rate, error rate, latency (RED method), saturation.

📋
Logs

Tool: ELK Stack or Loki
Structured JSON logs with consistent fields: timestamp, level, service, trace_id, user_id.
Key: Structured logging enables searching and aggregation in log platforms.

🔍
Traces

Tool: Jaeger, Zipkin, or AWS X-Ray
Distributed request tracing: follows a request through multiple services, showing timing and errors at each hop.
Key: OpenTelemetry is the standard for instrumentation.

Glossary of Key Terms

▼
📦 ADR (Architecture Decision Record)
A document that captures an important architectural decision made during a project, along with its context, consequences, and the alternatives considered. Helps teams understand why the codebase looks the way it does.
🤖 Agentic AI
AI systems that autonomously plan, use tools, observe results, and iterate toward a goal without requiring human input at every step. Examples include GitHub Copilot Agent and Cursor Agent mode.
🏃 Agile
A software development philosophy emphasizing iterative development, collaboration, and rapid response to change. Agile methodologies include Scrum, Kanban, and XP (Extreme Programming).
🗃️ Alembic
A database migration tool for SQLAlchemy. Allows you to version-control your database schema and apply incremental changes (migrations) as your application evolves.
⚫ Black
The "uncompromising" Python code formatter. Enforces a consistent code style by reformatting code according to its rules, with minimal configuration options.
🔒 CORS (Cross-Origin Resource Sharing)
A browser security mechanism that controls how web pages can make requests to a different domain than the one that served the web page. FastAPI's CORSMiddleware handles this configuration.
🖱️ Cursor IDE
An AI-first code editor built on VS Code, featuring deep AI integration including Composer (multi-file editing), Chat (codebase Q&A), and Agent mode for autonomous coding tasks.
📦 Dependency Injection
A design pattern where components receive their dependencies from external sources rather than creating them internally. FastAPI's Depends() system implements DI for route handlers.
📊 DORA Metrics
Four key metrics for measuring software delivery performance: Deployment Frequency, Lead Time for Changes, Mean Time to Recovery (MTTR), and Change Failure Rate. Defined by the DevOps Research and Assessment team.
🏠 DRY (Don't Repeat Yourself)
Software engineering principle stating that "every piece of knowledge must have a single, unambiguous, authoritative representation within a system." Duplicate code leads to maintenance nightmares.
⚡ FastAPI
A modern, fast Python web framework for building APIs, based on standard Python type hints. Provides automatic OpenAPI documentation, data validation via Pydantic, and async support out of the box.
🌊 GitFlow
A branching strategy using main, develop, feature, release, and hotfix branches. Used for projects with scheduled release cycles. Contrast with trunk-based development for CI/CD.
🤝 GitHub Copilot
An AI pair programming tool by GitHub (powered by OpenAI) that provides code suggestions in the IDE, powered by large language models trained on billions of lines of public code.
🔗 GraphQL
A query language for APIs that allows clients to request exactly the data they need. Unlike REST, which exposes fixed endpoints, GraphQL exposes a single endpoint with a typed schema.
🔷 JWT (JSON Web Token)
A compact, URL-safe token format for representing claims between two parties. Commonly used for authentication: the server issues a signed JWT, and the client includes it in subsequent requests.
⬇️ Lazy Loading
Loading data or resources only when they are first needed, rather than at startup. In SQLAlchemy, relationships can be lazy (loaded on access) or eager (loaded in the same query).
🔍 LSP (Language Server Protocol)
A protocol that standardizes how code editors communicate with language servers to provide features like autocomplete, go-to-definition, error highlighting, and refactoring.
🔧 Mypy
A static type checker for Python that analyzes type hints to catch type errors before runtime. Running mypy in strict mode provides the highest confidence in type correctness.
📡 OpenTelemetry
An open-source observability framework for generating, collecting, and exporting telemetry data (metrics, logs, traces) from distributed systems. Now the industry standard for instrumentation.
🔮 PEP (Python Enhancement Proposal)
A design document providing information to the Python community or describing a new feature. PEP 8 is the style guide. PEP 484 introduced type hints. PEP 20 is the Zen of Python.
🏗️ Protocol (Python)
A Python typing concept (PEP 544) for structural subtyping. A class satisfies a Protocol if it has the required methods/attributes, without explicitly inheriting from the Protocol class.
📊 Pydantic
A Python library for data validation and settings management using Python type hints. Pydantic v2 (2023) is significantly faster than v1 and is the default for FastAPI and many modern Python apps.
🧪 Pytest
The leading Python testing framework. Features include fixtures, parametrize, excellent plugin ecosystem, and detailed failure reports. The de-facto standard for modern Python testing.
🗃️ Repository Pattern
A design pattern that abstracts data access logic behind an interface, separating business logic from database code. Enables swapping databases, mocking in tests, and adhering to DIP.
⚡ Ruff
An extremely fast Python linter and formatter written in Rust. Replaces flake8, isort, pyupgrade, and many other tools. 10-100x faster than traditional Python linters.
📐 SOLID
Five OOP design principles: Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, Dependency Inversion. Introduced by Robert C. Martin as guidance for maintainable software design.
🗄️ SQLAlchemy
Python's most popular SQL toolkit and ORM. SQLAlchemy 2.0 (2023) introduced a modernized, type-safe API with mapped_column() and async support as first-class features.
�� Trunk-Based Development
A source-control practice where all developers commit to a shared trunk (main branch) frequently (at least daily). Enables true continuous integration and is preferred by high-performing teams.
🔷 Type Hints
Python syntax (PEP 484) for annotating variables, function parameters, and return types. Type hints are not enforced at runtime but enable static analysis tools (mypy, Pyright) to catch type errors.
🎵 Vibe Coding
Term coined by Andrej Karpathy describing a mode of development where the developer leans heavily on AI suggestions, accepting them without fully reading the code. Productive for prototypes; risky for production.
🌐 WebSocket
A communication protocol that provides full-duplex communication channels over a single TCP connection. Enables real-time features like chat, live dashboards, and collaborative editing. FastAPI has native WebSocket support.
